# AI setup, tradeoffs and limits

OpenRouter is retained rather than introducing another account/provider integration. It supports model selection and provider filters. No key is in the app; authenticated callable functions are the only client entrypoint.

## Model choice
The model is an explicit operator choice in `AI_MODEL`, blank by default. A cost-first evaluation candidate is `nvidia/nemotron-3.5-super-vl:free`: the public model catalog reported vision input and structured output support at implementation time. Free endpoints can be rate limited or fail the strict privacy filters; manual logging remains available. A paid candidate is the same model without `:free` (catalog snapshot: $0.15 input / $0.50 output per million tokens). This is a metadata-based candidate, not a quality/privacy certification. No paid inference was made and no credits were purchased.

Before enabling anything, verify current [model metadata](https://openrouter.ai/api/v1/models), provider availability, vision/structured schema behavior, portion accuracy, bilingual responses, pricing and contractual handling of health-related content. Choosing a free model does not make Firebase functions free; deployment may require a billing-enabled Firebase plan. Ask the owner before provisioning or enabling billing.

Requests require `data_collection: deny`, `zdr: true`, all parameters supported, no fallback route, and price caps of $0.30 input / $1.20 output per million tokens. A model may be listed while no route meets these constraints; this correctly fails closed. See [provider routing](https://openrouter.ai/docs/guides/routing/provider-selection) and [privacy policy](https://openrouter.ai/privacy/). Provider policies must be reviewed independently; request flags are not a legal guarantee.

## Runtime controls
- Input max 2,000 characters; photo JPEG data URL max 1,800,000 characters, 1,024px longest edge, no EXIF. No arbitrary remote image URL or SSRF fetch.
- Strict JSON schema plus Zod parsing; max 20 items, bounded finite quantities/nutrients, bounded answer length. Invalid outputs never enter the diary.
- 12-second timeout per provider attempt, one retry only on transient/timeout errors, 1,600 output tokens; client timeout 35s, function timeout 40s.
- Atomic 10/user/UTC-day and 2/user/minute quota plus 200 total/day. Failed calls count against quota to limit abuse. Two function instances cap concurrent infrastructure growth. There is no automatic unlimited queue or provider/model fallback.
- Character/token/image caps and price filters reduce exposure but are not a hard currency cap. Configure a separate provider key credit limit, Firebase budget alerts and monitoring. Firebase budget alerts do not stop spending.
- Production requires Auth, verified email, consent stored on the user's profile and App Check. Emulator bypasses email/App Check solely in the demo project. Never disable attestation to work around production setup.
- User messages/images are untrusted. System policy limits the assistant to general education; a bilingual pattern guard intercepts some dangerous requests/results. This is not comprehensive moderation or a clinically validated safety system. Adversarial testing and specialist review remain release gates.

## Privacy and confirmation
Only the submitted text/photo is transmitted. Chat context is bounded to recent turns in memory; no automatic profile sharing. Weekly requests send only logged-day counts, mean kg and mean recorded calories. Counts may identify sparse personal patterns, so consent is still necessary. Original photographs are never uploaded to Firebase Storage. No model output or private conversation is persisted by the app unless the user confirms a food in the editor. Each confirmed item preserves `source: ai`. Turning off AI clears visible AI results and prevents future calls; it cannot retract data already sent.

## Known release blocker
Web App Check accepts `EXPO_PUBLIC_RECAPTCHA_SITE_KEY` and initializes the Firebase web provider. The native bridge is implemented in `services/appCheck.native.ts`: React Native Firebase obtains App Attest/DeviceCheck or Play Integrity tokens, then a Firebase JS CustomProvider forwards them to the existing callable client. It initializes lazily after AI consent and uses JWT expiration rather than inventing a lifetime. It is not device-verified. Set `EXPO_PUBLIC_NATIVE_APP_CHECK_ENABLED=true` only in configured native builds; include matching `GoogleService-Info.plist` / `google-services.json` through ignored files or EAS file variables `GOOGLE_SERVICES_PLIST` / `GOOGLE_SERVICES_JSON`. Dynamic `app.config.ts` adds the native plugins and static iOS frameworks. Register the same identifiers/project in Firebase App Check and enable App Attest/DeviceCheck and Play Integrity. This requires a rebuilt signed development client; Expo Go cannot attest. No debug bypass is shipped. Verify real token acceptance and refresh on both platforms before enabling production AI. [Native provider documentation](https://rnfirebase.io/app-check/usage), [Firebase CustomProvider](https://firebase.google.com/docs/app-check/web/custom-provider).
