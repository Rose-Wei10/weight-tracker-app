# Design and data contracts

## Design system
Forma uses warm cream, forest green and restrained clay accents. Native system typography avoids extra font startup work. Shared controls define 48px action heights, rounded fields/cards, readable muted text, visible labels, semantic roles and bounded progress values. Layout uses available width, wraps small grids and caps tablet/web content width. Dark mode follows the operating system. Tab haptics respect platform behavior. Reduced-motion friendly: no essential or autoplay animation. Chart tooltips expose selected values in text; full screen-reader chart navigation still needs device QA.

## Metrics
- Canonical units: kg, cm, kcal, grams. Height in imperial is entered as total inches and displayed as feet/inches. Conversion: 1 kg = 2.2046226218 lb; 1 inch = 2.54 cm. Entry display rounding is one decimal; changing preferences does not rewrite historical records.
- Local date uses device year/month/day. UTC noon is only used for calendar arithmetic to avoid DST-length errors. Date validation rejects impossible dates. Refresh on foreground and every 30 seconds supports midnight rollover. Changing time zone does not retrospectively shift a saved calendar date.
- Seven-day moving mean averages recorded days within [date-6,date], with no interpolation or zero fill. Charts connect recorded dates at even chart positions; they are not a uniform elapsed-time scale. Calendar remains the precise date view.
- Duplicate dates are preserved. Analytics sorts IDs lexically and selects the final ID for each date consistently. This is deterministic, not a claim of latest edit time. New daily IDs plus transactional date claims prevent concurrent new-client duplicates. Old released clients must be retired before rules deployment: random-ID weight creation is intentionally rejected by the new rules. Existing random-ID records remain readable/editable.
- Goal progress: clamp((current-start)/(goal-start),0,1). Supports gain and loss. When start=goal, progress is 100% only at that weight; no arbitrary maintenance tolerance is implied.
- Weekly weight change compares means of recorded days in current/prior seven-day windows. Logging consistency counts unique weight dates/30.
- Diary entries store TOTAL nutrition for the recorded quantity. Changing quantity scales totals once. Food labels/portions differ; user reviews all values. Old missing macro values contribute no known grams and are visibly flagged as incomplete.
- Nutrition averages exclude unlogged days. Partial diaries may underestimate intake; no intake is inferred for missing days. Monthly summaries count entries and days, not predicted health outcomes.
- Estimated maintenance: Mifflin–St Jeor = 10×kg + 6.25×cm − 5×age + sex coefficient (−161 or +5), multiplied by self-reported activity. Gradual loss/gain adjusts by 10%; maintenance is unchanged. Software target bounds 1,200–6,000 are validation limits, not personalized clinical safety thresholds. Formula is restricted to adult profiles. A conservative software guard refuses loss estimates when the current adult BMI ratio is below 18.5 and refuses lower goals below that threshold; this guard is not a diagnosis or a complete safety assessment. [Original paper](https://pubmed.ncbi.nlm.nih.gov/2305711/).
- Macro display guides allocate 25%/45%/30% energy to protein/carbs/fat, using 4/4/9 kcal/g. These are illustrative guides, not individualized prescriptions.
- BMI = kg/(height metres²), shown without diagnostic categories. BMI cannot measure body composition and must not stand alone as a health assessment. [CDC explanation](https://www.cdc.gov/bmi/about/).

## Compatibility and isolation
No automatic database migration. Profile updates merge; exports query original records so records that fail the display schema are not silently lost. Legacy field warnings remain visible. Strict new rules intentionally change the client write contract; stage them with the updated client and test a production backup in a separate staging project first. Never deploy blindly over unknown production rules.

One AppProvider owns session state and listeners. All listeners unsubscribe on user change, and records are hidden immediately if their owner differs from the current user. Shared data drives both dashboard and diary. Snapshot failures are visible and retryable. Native auth explicitly uses AsyncStorage persistence; web uses Firebase's browser persistence. Firestore native offline persistence is not enabled by this implementation; do not promise offline writes across app restarts.

User subcollections are ownership-restricted. Schemas validate writes on client and server; rules independently bound nutrition and profile data. Unknown paths and server counters deny all client access. Clients cannot delete profile documents directly. Deletion requires recent reauthentication, explicit confirmation, a temporary write-block tombstone, recursive data cleanup and Auth deletion. TTL for deletion tombstones is an operator setup requirement; failed deletion is retryable while Auth account exists. Operational Firebase logs/backups have separate retention and are not erased by document deletion.

## Scale and observability limits
Current listeners read full weight/food histories for complete analytics, frequent foods and export. This is suitable for validation with small personal datasets, not a proven scale design. Add range queries/pagination and denormalized summaries only after measurements justify them. Images remain in temporary device cache; originals stay in the user's photo library. Exports are removed from the app cache after sharing. App code does not log meals, photos, passwords, auth tokens or provider errors. Firebase infrastructure may log request metadata; configure retention and budgets. Crash reporting is deferred until vendor/region/consent and redaction are chosen.
